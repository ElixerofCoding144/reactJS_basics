# 1. Initial Project Setup

Install Node.js using Homebrew:

```bash
brew install node
```

Check the installed versions:

```bash
node -v
npm -v
```

Example:

```text
v26.7.0
11.19.0
```

Initialize a Node project:

```bash
npm init
```

Or, if we want npm to accept the defaults automatically:

```bash
npm init -y
```

Install Parcel:

```bash
npm install -D parcel
```

Install React and React DOM:

```bash
npm install react react-dom
```

Start the Parcel development server:

```bash
npx parcel index.html
```

Parcel runs a development server on:

```text
http://localhost:1234
```

Parcel's official documentation distinguishes the development command from the production build command. `parcel index.html` starts the dev server, while `parcel build index.html` produces an optimized production build. ([Parcel][1])

# 2. Why Do We Need `package.json`?

### Interview Answer

`package.json` is the **manifest/configuration file of a Node.js project**.

It contains important information about our application, such as:

* project name
* project version
* npm scripts
* dependencies
* devDependencies
* package versions
* browser configuration
* project metadata
* Node/npm requirements
* other tooling configuration

Example:

```json
{
  "name": "my-react-app",
  "version": "1.0.0",
  "scripts": {
    "dev": "parcel index.html",
    "build": "parcel build index.html"
  },
  "dependencies": {
    "react": "...",
    "react-dom": "..."
  },
  "devDependencies": {
    "parcel": "..."
  }
}
```

Think of `package.json` as the **configuration/manifest of the project**.

It tells npm and other developers:

> "These are the packages, scripts, and configuration required by this application."

npm recognizes dependency declarations, scripts, version ranges, and many other project settings through `package.json`. ([npm Docs][2])

# 3. What is a Bundler?

### Interview Answer

A **bundler** is a tool that takes our application's source files and dependencies, processes them, and generates optimized files that can be served to the browser.

For example, our application might contain:

```text
App.js
Header.js
Footer.js
utils.js
styles.css
logo.png
React
ReactDOM
other npm packages
```

The bundler analyzes the dependency graph and produces browser-ready output.

Popular bundlers/build tools include:

* Parcel
* Webpack
* Vite
* Rollup
* esbuild-based tooling

Historically, Create React App used Webpack together with Babel and other tooling.

### Why Do We Need a Bundler?

Because production applications require more than simply sending our raw source files to the browser.

A bundler/build tool can handle:

```text
Source Code
     ↓
Dependency Resolution
     ↓
Transformation / Transpilation
     ↓
Bundling
     ↓
Tree Shaking
     ↓
Minification
     ↓
Code Splitting
     ↓
Content Hashing
     ↓
Production Files
```

# 4. How to Install Parcel

Install Parcel as a **development dependency**:

```bash
npm install --save-dev parcel
```

Short form:

```bash
npm install -D parcel
```

Why `-D`?

Because Parcel is required for **developing and building the application**, but Parcel itself is not part of the JavaScript code that runs in the user's browser.

npm stores packages installed with `-D` under `devDependencies`. ([npm Docs][3])

---

# 5. What Does Parcel Provide?

Parcel is a zero-configuration build tool that provides many features out of the box. ([Parcel][1])

### 1. Development Server

```bash
npx parcel index.html
```

Starts a local development server.

Default:

```text
http://localhost:1234
```

---

### 2. Hot Reloading / HMR

When we modify our code, Parcel can update the browser automatically.

With React, Parcel also supports **Fast Refresh**, which can preserve component state while developing. ([Parcel][1])

---

### 3. File Watching

Parcel watches project files and rebuilds the affected parts whenever something changes.

It uses efficient native filesystem mechanisms for change detection. ([Parcel][1])

---

### 4. Caching

Parcel caches previous build work.

For example:

```text
First Build
   ↓
Transform A
Transform B
Transform C

Second Build
   ↓
Only changed files need significant work
```

This makes subsequent development builds faster.

Parcel stores build-related cache information in:

```text
.parcel-cache/
```

Parcel tracks files, configuration, plugins, and build dependencies so that it can invalidate only the necessary parts of its cache. ([Parcel][1])

---

### 5. Minification

Production code is reduced in size.

Example:

```javascript
function calculateTotal(price, quantity) {
  return price * quantity;
}
```

may be optimized into something conceptually similar to:

```javascript
function a(b,c){return b*c}
```

Parcel includes minification support for JavaScript, CSS, HTML, and SVG. ([Parcel][1])

---

### 6. Tree Shaking

Tree shaking removes code that is never used.

Example:

```javascript
export function add(a, b) {
  return a + b;
}

export function subtract(a, b) {
  return a - b;
}
```

If we import only:

```javascript
import { add } from "./math";
```

the unused `subtract` function may be removed from the production output.

Parcel performs static analysis of module imports and exports to tree-shake unused code. ([Parcel][1])

---

### 7. Code Splitting

Instead of producing one enormous JavaScript file, Parcel can create multiple bundles.

Example:

```text
main.js
checkout.js
profile.js
vendor.js
```

Code can therefore be loaded only when necessary.

Parcel supports automatic code splitting and creation of shared bundles. ([Parcel][1])

---

### 8. Content Hashing

Production filenames may contain hashes:

```text
app.a83df29.js
styles.f918ac3.css
```

If the file's content changes, its hash changes.

This is useful for **browser cache invalidation**.

For example:

```text
app.abc123.js
      ↓ code changed
app.xyz987.js
```

The browser sees a new filename and downloads the updated resource. Parcel calls this **content hashing**, rather than "consistent hashing." ([Parcel][1])

---

### 9. Image Optimization

Parcel can resize, convert, and optimize images during the build process. ([Parcel][1])

---

### 10. Differential Bundling

Different JavaScript can be generated depending on the browser capabilities.

For example:

```text
Modern Browser
      ↓
Modern JavaScript bundle

Older Browser
      ↓
Compatible legacy bundle
```

Parcel can automatically produce modern and legacy outputs according to configured browser targets. ([Parcel][1])

---

### 11. Browser Compatibility / Transpilation

Parcel can transpile JavaScript according to the browsers our application supports.

This configuration is generally controlled through:

```json
"browserslist": [...]
```

Parcel uses those targets to determine what transformations are required. ([Parcel][1])

---

### 12. Diagnostics

Parcel provides readable compilation errors containing:

* file location
* line number
* error description
* code frame
* possible fixes

([Parcel][1])

---

### 13. HTTPS Development Server

Parcel can run its development server over HTTPS:

```bash
npx parcel index.html --https
```

([Parcel][1])

---

### Important Correction: Compression vs Minification

**Minification and compression are not the same thing.**

Minification:

```text
Readable JS
     ↓
Remove whitespace / shorten / optimize
     ↓
Minified JS
```

HTTP compression:

```text
JavaScript
    ↓
gzip / Brotli
    ↓
Compressed network response
```

Production servers and CDNs commonly handle HTTP compression separately.

# 6. `dependencies` vs `devDependencies`

## dependencies

Packages required by the actual application are placed under:

```json
"dependencies": {}
```

Example:

```json
{
  "dependencies": {
    "react": "...",
    "react-dom": "..."
  }
}
```

React is part of our application's runtime code, so it belongs in `dependencies`.

---

## devDependencies

Packages required primarily for:

* development
* compilation
* bundling
* testing
* linting
* formatting

are usually placed under:

```json
"devDependencies": {}
```

Example:

```json
{
  "devDependencies": {
    "parcel": "..."
  }
}
```

npm officially supports `npm install -D`/`--save-dev` for adding packages to `devDependencies`. ([npm Docs][3])

### Interview Answer

> `dependencies` are packages required by our application, whereas `devDependencies` are tools primarily required during development or the build process.

Examples:

```text
dependencies
├── react
└── react-dom

devDependencies
├── parcel
├── eslint
└── prettier
```

# 7. Caret `^` vs Tilde `~`

Suppose:

```json
"react": "^19.1.0"
```

Semantic versioning follows:

```text
MAJOR.MINOR.PATCH

19.1.0
│  │ │
│  │ └── Patch
│  └──── Minor
└─────── Major
```

---

## Caret `^`

```json
"package": "^1.2.3"
```

Generally means:

```text
>= 1.2.3
<  2.0.0
```

So these can match:

```text
1.2.4 ✅
1.3.0 ✅
1.9.5 ✅
2.0.0 ❌
```

For versions `>=1.0.0`, caret generally allows **minor and patch updates but not the next major version**.

There are special rules for `0.x` releases. For example, `^0.2.3` resolves below `0.3.0`. ([GitHub][4])

---

## Tilde `~`

```json
"package": "~1.2.3"
```

means approximately:

```text
>= 1.2.3
<  1.3.0
```

Allowed:

```text
1.2.4 ✅
1.2.9 ✅
1.3.0 ❌
```

Tilde is therefore more restrictive and generally allows only patch changes when major, minor, and patch are specified. ([GitHub][4])

---

## Quick Comparison

| Version  | Allowed updates          |
| -------- | ------------------------ |
| `^1.2.3` | `1.x.x`, but not `2.0.0` |
| `~1.2.3` | `1.2.x`, but not `1.3.0` |
| `1.2.3`  | Exactly `1.2.3`          |

### Easy Interview Trick

```text
^ → minor + patch changes
~ → patch changes
```

For normal versions `>=1.0.0`.

# 8. `package.json` vs `package-lock.json`

This is a very common interview question.

## `package.json`

Defines the dependencies our project **accepts**.

Example:

```json
{
  "dependencies": {
    "react": "^19.1.0"
  }
}
```

The caret represents a version range.

---

## `package-lock.json`

Records the **exact dependency tree that npm resolved and installed**.

Conceptually:

```json
{
  "node_modules/react": {
    "version": "19.x.x",
    "resolved": "...",
    "integrity": "sha512-..."
  }
}
```

npm documents that the lockfile describes the exact dependency tree and is intended to be committed so that teammates, CI systems, and deployments can recreate the same tree. ([npm Docs][5])

### Interview Answer

> `package.json` specifies the acceptable dependency ranges and project configuration, while `package-lock.json` records the exact resolved dependency tree to make installations reproducible.

---

# 9. What is `integrity` in `package-lock.json`?

Example:

```json
{
  "integrity": "sha512-AbCdEf..."
}
```

### Interview Answer

The `integrity` field contains a cryptographic hash representing the package artifact npm downloaded.

npm can use this integrity information to verify that the downloaded package content matches the expected content.

Conceptually:

```text
Download Package
       ↓
Calculate Hash
       ↓
Compare with integrity value
       ↓
Match?
  ↙           ↘
Yes            No
Continue        Integrity failure
```

Current npm lockfiles store `sha512` or `sha1` Standard Subresource Integrity values for package artifacts. ([npm Docs][5])

### Why is it useful?

It provides protection against:

* corrupted downloads
* unexpected package content changes
* tampered artifacts

---

# 10. What is `resolved` in `package-lock.json`?

Example:

```json
{
  "resolved": "https://registry.npmjs.org/..."
}
```

### Interview Answer

`resolved` indicates **where npm resolved/downloaded that particular dependency from**.

For a registry dependency, it can point to the package tarball.

It can also represent locations for:

* registry packages
* Git dependencies
* linked dependencies

npm describes `resolved` as the location from which the package was actually resolved. ([npm Docs][5])

# 11. What is a Transitive Dependency?

Suppose our application installs:

```text
Our Application
      |
      └── Parcel
            |
            └── Package A
                  |
                  └── Package B
```

We directly installed:

```text
Parcel
```

But Parcel itself requires:

```text
Package A
```

and Package A requires:

```text
Package B
```

Then Package A and Package B are **transitive dependencies** of our project.

### Interview Answer

> A transitive dependency is a dependency of one of our dependencies rather than a package that we directly installed.

Example:

```text
My App
 └── A          ← direct dependency
      └── B     ← transitive dependency
           └── C ← transitive dependency
```

This is one reason installing one package can result in many packages appearing inside `node_modules`.

---

# 12. What is Browserslist?

Browserslist defines **which browsers our application intends to support**.

It can be configured in `package.json`:

```json
{
  "browserslist": [
    "> 1%",
    "last 2 versions",
    "not dead"
  ]
}
```

Tools can use this configuration when deciding:

* which JavaScript features need transpiling
* which CSS features need prefixes
* which browser-specific transformations are required

Browserslist is used by tools such as Babel, Autoprefixer, and other frontend tooling, and Parcel can use a project's Browserslist targets when transpiling. ([GitHub][6])

### Interview Answer

> Browserslist is a shared configuration that tells frontend tools which browser versions our application needs to support.

# 13. How Many `package.json` Files Are There?

This question has a slightly tricky answer.

### In our application's root

Normally, there is **one main `package.json`**:

```text
project/
└── package.json
```

But installed npm packages generally have their own package metadata too.

Conceptually:

```text
project/
├── package.json
│
└── node_modules/
    ├── react/
    │   └── package.json
    │
    ├── react-dom/
    │   └── package.json
    │
    └── parcel/
        └── package.json
```

Therefore:

> There is normally one root `package.json` representing our application, but dependencies inside `node_modules` can also contain their own `package.json` files.

So the total number is **not fixed**.

# 14. What is the `dist` Folder?

`dist` stands for:

```text
distribution
```

It contains the **built/optimized files that are intended for deployment**.

When we run:

```bash
npx parcel build index.html
```

Parcel processes our application and produces optimized production assets.

Conceptually:

```text
src/
├── App.js
├── Header.js
├── Footer.js
└── styles.css

        ↓ Parcel Build

dist/
├── index.html
├── app.<hash>.js
└── styles.<hash>.css
```

The generated output can include:

* bundled JavaScript
* minified JavaScript
* processed CSS
* optimized HTML
* content-hashed files
* code-split bundles
* processed assets

Parcel performs production optimizations such as tree shaking, minification, content hashing and automatic code splitting. ([Parcel][1])

# 15. What Should Be Pushed to GitHub?

This is an important correction.

## `node_modules`

❌ **Do not push**

```text
node_modules/
```

It is huge and can be recreated using npm.

---

## `package.json`

✅ **Push it**

```text
package.json
```

This is essential project configuration.

---

## `package-lock.json`

✅ **Push it**

```text
package-lock.json
```

This should generally be committed because it makes dependency installation reproducible. npm explicitly states that `package-lock.json` is intended to be committed into source repositories. ([npm Docs][5])

---

## `dist`

Usually:

❌ **Do not push it**

```text
dist/
```

It is normally generated during CI/CD.

However, there are deployment setups where generated artifacts are intentionally committed. That is a deployment decision rather than a universal rule.

---

## `.parcel-cache`

❌ **Do not push**

```text
.parcel-cache/
```

It is a generated build cache.

---

### Typical Git Repository

```text
project/
├── src/
├── index.html
├── package.json           ✅
├── package-lock.json      ✅
├── .gitignore             ✅
│
├── node_modules/          ❌
├── dist/                  ❌ usually
└── .parcel-cache/         ❌
```

# 16. What is `.gitignore`?

`.gitignore` tells Git which files or directories should **not be tracked**.

Example:

```gitignore
node_modules/
dist/
.parcel-cache/
.DS_Store
.env
```

Without `.gitignore`, we could accidentally commit:

```text
node_modules/
build artifacts
cache files
environment files
OS-generated files
```

### Interview Answer

> `.gitignore` defines files and directories that Git should ignore and not track in version control.

# 17. How to Regenerate `node_modules`

Suppose we delete it:

```bash
rm -rf node_modules
```

We can regenerate dependencies with:

```bash
npm install
```

npm reads:

```text
package.json
package-lock.json
```

and restores the dependency tree.

When the lockfile is compatible with `package.json`, npm uses the locked versions during installation. ([npm Docs][7])

---

## What About Production / CI?

For CI/CD, prefer:

```bash
npm ci
```

`npm ci` is specifically designed for clean, reproducible installs in automated environments.

It:

* requires `package-lock.json`
* installs according to the lockfile
* fails if `package.json` and the lockfile disagree
* removes an existing `node_modules` directory
* does not modify `package.json` or the lockfile

([npm Docs][8])

### Development

```bash
npm install
```

### CI / Production Build Pipeline

```bash
npm ci
```

# 18. npm vs npx

Another common interview question.

## npm

**npm = Node Package Manager**

It is primarily used to:

* install packages
* uninstall packages
* manage dependencies
* run package scripts
* manage package versions

Example:

```bash
npm install react
```

This installs React.

Another example:

```bash
npm run build
```

This executes a script defined in `package.json`.

---

## npx

`npx` is used to **execute a command exposed by an npm package**.

Example:

```bash
npx parcel index.html
```

Parcel is installed locally:

```text
node_modules/
└── .bin/
    └── parcel
```

`npx` finds and executes that binary.

Modern `npx` is built around npm's package execution functionality, and it can execute locally installed package binaries or resolve packages when necessary. ([npm Docs][9])

### Easy Interview Answer

```text
npm → installs/manages packages

npx → executes package binaries
```

For example:

```bash
npm install -D parcel
```

installs Parcel.

```bash
npx parcel index.html
```

executes Parcel.

# 19. Development Build vs Production Build

This is another important correction.

## Development

```bash
npx parcel index.html
```

This starts the development server.

It is used while coding.

Features include:

* development server
* hot reloading
* file watching
* diagnostics
* caching

([Parcel][1])

---

## Production

Use:

```bash
npx parcel build index.html
```

**Not:**

```bash
npx parcel index.html
```

The second command is primarily the development server command.

Parcel's production build performs optimizations including minification and tree shaking. ([Parcel][1])

---

## Better Approach: npm Scripts

Instead of remembering Parcel commands, define scripts:

```json
{
  "scripts": {
    "dev": "parcel index.html",
    "build": "parcel build index.html"
  }
}
```

Then:

### Development

```bash
npm run dev
```

### Production Build

```bash
npm run build
```

This is usually cleaner for teams and CI/CD pipelines.

# 20. Why Avoid CDN for React Dependencies?

Initially, React could be loaded using CDN scripts.

Example conceptually:

```html
<script src="https://some-cdn/react.js"></script>
<script src="https://some-cdn/react-dom.js"></script>
```

For a real application, installing dependencies using npm is usually preferable.

```bash
npm install react react-dom
```

React's documentation supports adding React to an existing project through npm with:

```bash
npm install react react-dom
```

([React][10])

---

## Advantages of npm Packages

### 1. Version Management

Dependencies are explicitly defined:

```json
{
  "dependencies": {
    "react": "...",
    "react-dom": "..."
  }
}
```

---

### 2. Reproducible Builds

`package-lock.json` records exactly what dependency tree was installed. ([npm Docs][5])

---

### 3. Bundler Integration

We can write:

```javascript
import React from "react";
```

and Parcel resolves the npm dependency.

---

### 4. Tree Shaking / Build Optimization

Bundlers can analyze imports and optimize the resulting application.

---

### 5. Better Developer Experience

npm dependencies integrate naturally with:

* IDEs
* TypeScript
* linters
* bundlers
* test runners
* CI/CD

---

### 6. No Runtime Dependency on a Third-Party CDN

Our application's dependency installation and bundling process is under our build pipeline's control.

---

### Are CDNs Bad?

No.

CDNs are extremely useful for serving static assets globally.

The point is that:

> For application dependencies such as React, a package manager + bundler generally gives us much stronger dependency management and build integration than manually adding CDN scripts.

CDNs can still make sense for:

* quick prototypes
* demos
* simple static pages
* special deployment architectures

# 22. `React is not defined` Error

Suppose we receive:

```text
Uncaught ReferenceError: React is not defined
```

For example:

```text
App.js:49:26
```

This means our code or the generated JSX code is referring to the `React` identifier, but `React` is not available in that module.

A straightforward fix is:

```javascript
import React from "react";
```

For React DOM:

```javascript
import { createRoot } from "react-dom/client";
```

React's current client API uses `createRoot` from `react-dom/client`. ([React][11])

---

## Example

### `App.js`

```javascript
import React from "react";

function App() {
  return <h1>Hello React!</h1>;
}

export default App;
```

### `index.js`

```javascript
import React from "react";
import { createRoot } from "react-dom/client";
import App from "./App";

const container = document.getElementById("root");
const root = createRoot(container);

root.render(<App />);
```

### `index.html`

```html
<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>React App</title>
  </head>

  <body>
    <div id="root"></div>

    <script type="module" src="./index.js"></script>
  </body>
</html>
```

Parcel supports JSX compilation out of the box. ([Parcel][1])

# 23. Recommended `package.json`

A simple project can look like this:

```json
{
  "name": "react-parcel-app",
  "version": "1.0.0",
  "private": true,
  "scripts": {
    "dev": "parcel index.html",
    "build": "parcel build index.html"
  },
  "dependencies": {
    "react": "<installed-version>",
    "react-dom": "<installed-version>"
  },
  "devDependencies": {
    "parcel": "<installed-version>"
  }
}
```

Do not manually copy version numbers from another project.

Let npm create them:

```bash
npm install react react-dom
npm install -D parcel
```

# 24. Recommended Project Structure

A simple React + Parcel project could look like:

```text
react-parcel-app/
│
├── src/
│   ├── App.js
│   ├── Header.js
│   ├── Footer.js
│   └── styles.css
│
├── index.js
├── index.html
│
├── package.json
├── package-lock.json
├── .gitignore
│
├── node_modules/
├── .parcel-cache/
└── dist/
```

Git normally tracks:

```text
src/
index.js
index.html
package.json
package-lock.json
.gitignore
```

and ignores:

```text
node_modules/
.parcel-cache/
dist/
```

# 25. Production Workflow

A clean production workflow is:

```text
Developer writes source code
          ↓
       Git Push
          ↓
          CI
          ↓
       npm ci
          ↓
    npm run build
          ↓
      Parcel
          ↓
        dist/
          ↓
Deploy dist/ to hosting/CDN
```

`npm ci` is intended for automated environments such as CI and deployment, while `parcel build index.html` generates Parcel's optimized production build. ([npm Docs][8])

# 26. Quick Interview Revision

## What is `package.json`?

> `package.json` is the manifest of a Node.js project. It contains project metadata, scripts, dependencies, devDependencies, version requirements, and tooling configuration.

---

## What is a bundler?

> A bundler processes our source files and dependencies and generates optimized browser-ready assets.

---

## Why Parcel?

> Parcel provides a development server, hot reloading, caching, JSX transformation, bundling, tree shaking, minification, code splitting, content hashing, image optimization, browser-targeted transpilation, and production optimizations with minimal configuration. ([Parcel][1])

---

## Dependency vs DevDependency?

> Dependencies are required by the application, whereas devDependencies are primarily needed during development, testing, or the build process.

```text
React  → dependency
Parcel → devDependency
```

---

## `^` vs `~`?

```text
^1.2.3 → >=1.2.3 <2.0.0
~1.2.3 → >=1.2.3 <1.3.0
```

([GitHub][4])

---

## `package.json` vs `package-lock.json`?

> `package.json` specifies acceptable dependency ranges, while `package-lock.json` records the exact dependency tree npm resolved.

---

## What is `integrity`?

> A cryptographic integrity hash used to verify the downloaded package artifact.

---

## What is `resolved`?

> The location from which npm resolved a dependency, such as a registry tarball URL.

([npm Docs][5])

---

## What is a transitive dependency?

> A dependency required by one of our dependencies rather than something we directly installed.

```text
App → Parcel → A → B

Parcel = direct
A/B    = transitive
```

---

## What is Browserslist?

> Browserslist defines which browsers our application supports so tools such as Parcel, Babel, and Autoprefixer can perform the appropriate transformations. ([GitHub][6])

---

## Should `node_modules` be committed?

> No. It can be recreated from the package manifest and lockfile.

---

## Should `package.json` be committed?

> **Yes.**

---

## Should `package-lock.json` be committed?

> **Yes.** It helps ensure reproducible dependency installations. ([npm Docs][5])

---

## How do we restore `node_modules`?

Development:

```bash
npm install
```

CI/production build:

```bash
npm ci
```

---

## npm vs npx?

```text
npm → install/manage packages and run scripts
npx → execute package binaries
```

---

## Start Parcel development server?

```bash
npm run dev
```

Equivalent to:

```bash
npx parcel index.html
```

---

## Create Parcel production build?

```bash
npm run build
```

Equivalent to:

```bash
npx parcel build index.html
```

---

## Install React?

```bash
npm install react react-dom
```

---

```bash
# Initialize project
npm init -y

# Install Parcel
npm install -D parcel

# Development
npm run dev

# Production build
npm run build

npm ci
```
